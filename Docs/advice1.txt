二、 对 Opus 方案的审视：有哪 3 处隐患需要补充或修正？

没有任何一份方案是十全十美的。结合实际 C++ 工业软件开发经验，Opus 方案中有 3 个地方存在潜在隐患，建议在立项时予以修正：

1. 隐患一：过度依赖 OCCT 原生 AIS_Manipulator 做 6D 路径点拖拽（M03）
问题所在：虽然用 OCCT AIS 做边/面拾取非常爽，但 OCCT 自带的 AIS_Manipulator（三维坐标轴拖拽控件）在工业界是出了名的“难用”——它的视觉缩放逻辑、局部坐标系/参考坐标系切换、旋转角度吸附（Snapping）非常生硬，且在鼠标拖拽过程中如果直接修改对象变换，很难与“机器人实时逆解跟随 + 碰撞变色”流畅配合。
修正建议：框架继续用 OCCT AIS，但不要直接裸用默认的 AIS_Manipulator。在阶段 1 需预留约 1 周时间，基于 AIS_InteractiveObject 派生定制一个专用的 TcpGizmoManipulator：鼠标拖动时只发出 PreviewPoseChanged 信号驱动机器人临时正解/逆解预览，鼠标松开（MouseRelease）时才打包生成一条 ModifyTargetPoseCommand 压入 Undo 栈。
2. 隐患二：将“开源自研 3D PDF 骨骼动画”列为 P0 的投入产出比风险（M13）
问题所在：Opus 虽然意识到了 3D PDF 的风险，但仍在 M13 中把“通过 IDTF
→
→U3D + libHaru/PoDoFo 手写 3D 注释字典 + Acrobat 3D JS 动画”定为了 P0（MVP 必须），而把“单文件 HTML（Three.js）动画导出”放在了 P1。
工程现实：开源的 U3D 转换库（源自 2007 年的 SourceForge 老代码）年久失修，手写 Acrobat 3D JavaScript 矩阵动画调试极其痛苦（可能耗费 3~4 周），而且现在客户电脑装了新版 Adobe Reader 默认也是黑屏禁止 3D 的。相反，导出一个**单文件离线可交互的 HTML5（内嵌精简 glTF 与关键帧动画，双击浏览器即可 60 帧丝滑播放、旋转、拖进度条）**只需要 2~3 天开发量。
修正建议：在阶段 0 预研时给开源 3D PDF 动画设定严格的 3~5 天熔断机制。如果开源 U3D 动画链路过于脆弱且不打算花几万美金买商业 SDK（HOOPS Publish / PDF3D），立刻将 “2D PDF 工艺报表（含静态多视角高清截图）+ 单文件离线 3D HTML 交互动画包” 提拔为 P0 标准交付物。
3. 隐患三：关于您提到的“将带机器人的场景导入”的范围界定（M05 vs 您的原始需求）
问题所在：您在最初描述需求时提到：“能够将带机器人的场景导入，编辑，路径编辑，预览，输出这一整条闭环做到即可”。
而在 Opus 的方案中，P0 阶段采用的是**“内置机器人库（软件自带配好运动学的机器人）+ 仅从外部导入工件/夹具 STEP”**；而把“从外部导入带机器人的场景（如 URDF 导入，或把静态 STEP 总装里的机器人绑定成可动关节）”放到了 P1（并在文末 第 12.6 条 向您提问）。
修正建议：这一点必须立刻明确——如果您手头的上游数据就是一个已经摆好机器人和工装的完整场景文件（比如一个整体 STEP、USD 或其他软件导出的格式），那么解析这个场景并绑定机器人运动学就必须提拔到 P0；如果您可以接受“在我们的软件里从列表拖出机器人，只导入外部工件 STEP”，那么 Opus 的切分是最省工期的。
